# TTRPG Toolkit

A personal, local-first, system-agnostic TTRPG toolkit for Windows and Android, shared with a small group of friends and built in nine phases. **Current phase: Phases 1 to 3 are complete; Phase 4 (worldbuilding) is next** (see "Phase 4 handoff" below). Phase 2 delivered: the whole Dice side (parser/roller, roll log, saved rolls, formulas, quick buttons), the Cards library (cards with pictures, sets, decks, pools), card draws with saved draws, decks in play, spreads, starter decks (playing cards, Tarokka), and the widget framework with the quick tools panel. Phase 3 delivered: random tables (weights and ranges, slots that roll dice, other tables and card draws, labels, unique picks, avoid-recent, entry tags), a slot-chip entry editor, rename-with-slot-update, the name generator (one tool drawing from chosen tables, with a tag filter and saved presets), content-pack support for all of it, quick widgets, and four starter sets of tables (fantasy names, tavern names, quirks and rumors, weather).

The full spec is [spec.md](spec.md). This file is a summary; when the two disagree, the spec wins (and tell Katie so the spec can be updated).

## Architecture in brief

- **Eight tools, each with its own library** (folders, tags, search): Worldbuilding (documents), Cards, Tables and generators, Maps, Calendar and timeline, Encounters, Dice, GM screen.
- **Five shared engines** underneath: fields, queries, results (dice/tables/draws/generators + roll log), campaign state, and links/tags. Tools plug into the engines instead of reimplementing them.
- **Module registry:** each module registers its tools, item types, embed types, field types, table slot types, widgets, command palette actions and content pack data. The core app picks them up automatically. New features should plug in here, not rewire the core.
- **Content packs:** one zip format (versioned) for backups, copying between campaigns and sharing.
- **Rulesets** are global; everything else lives in a campaign.

## Rules that come from the spec's principles

- **Local first, offline always.** Sync is an extra, never a requirement.
- **Every record has a UUID, timestamps and a soft-delete flag.** Never hard-delete library items; deleted items go to the trash with restore.
- **Schema is versioned with step-by-step migrations.** Migrations are append-only; never edit one that has shipped. Content packs carry a version too.
- **Data, not code,** for system-specific things (rulesets, dice, stat blocks, tables, templates).
- **Simple by default, deep on demand.** Advanced options go behind an "Advanced" toggle.
- **Secret content is never sent to a player's device,** not just hidden in the UI.
- **No outside apps required.** Imports are optional.
- Engines are *designed* in Phase 1 but *built* only when the first tool needs them. Keep the foundation small.

## Conventions

*Proposed at project start; edit freely.*

- TypeScript `strict` on; no `any` (use `unknown` and narrow).
- React function components and hooks only.
- npm is the package manager.
- Logic with tricky rules (dice parser, draw rules, calendar math, pathfinding, migrations) gets automated tests. Logic written in Rust is tested with `cargo test` (in `#[cfg(test)]` modules, using in-memory SQLite); logic written in TypeScript uses Vitest (`*.test.ts` next to the code). UI is checked by running the app.
- **Database lives in Rust** (`rusqlite`, bundled SQLite) in `src-tauri/src/db/`. React never touches SQL; it calls Tauri commands. The DB file is `toolkit.db` in the app data dir.
- **Migrations:** numbered `.sql` files in `src-tauri/migrations/`, registered in `src-tauri/src/db/migrations.rs`. Version is tracked in SQLite's `user_version`. To change the schema, add the next numbered file and entry; never edit an existing one.
- **Module registry** (`src/registry/`): a module is a `ModuleDefinition` object (id plus optional `tools`, `itemTypes`, `commands`, `widgets`; types in `registry/types.ts`). To add a feature: create `src/modules/<name>/index.ts` exporting a module, then add it to the list in `src/registry/index.ts`. The app shell (`App.tsx`) builds its navigation from `registry.getTools()`; the command palette will read `registry.getCommands()`. Core code must never import a specific module's screens directly. New contribution kinds (embed types, field types, widgets...) are added to the registry when the first feature needs them. Duplicate ids throw at startup.
- **Library items:** every item of every tool is a row in the shared `items` table (`library` = owning tool id, `item_type`, `folder_id`, `visibility` of `default|visible|secret`). Types needing more data get their own detail table keyed by the same id. Tags, links, search and trash work on `items`, so they work for every tool. Folders (`folders` table, nestable) belong to one tool's `library`; an item and its folder must share campaign and library. Data-layer code is in `src-tauri/src/db/{items,folders}.rs`; all errors use the shared `DbError` (`db/error.rs`).
- **Trash semantics:** deleting a folder soft-deletes its subfolders and items with the *same* `deleted_at`, so restoring the folder restores only that group (things deleted earlier stay deleted). `db/trash.rs` lists "roots of deletion" only, restores items/folders (falling back to the top level if the original parent is still trashed), and permanently deletes (`purge_*`, `empty` with an optional "older than" cutoff). Only trashed rows can be purged. Any table that references `items` (links...) must use `ON DELETE CASCADE` so purging works.
- **Tags** (`db/tags.rs`, migration 0003): campaign-wide, optional `#rrggbb` colour, nestable (loops refused), unique among live siblings ignoring case (checked in code and by a unique index). Soft-deleted with their sub-tags under one shared timestamp; restore mirrors folders and refuses a name clash. `item_tags` links carry timestamps and `deleted_at` (a removed link is kept, so removals can sync later; re-adding revives it). `tags::items_with_tag(.., include_subtags)` finds items by tag. Tags can only attach to live items/tags in the same campaign.
- **Tauri commands** all live in `src-tauri/src/commands.rs` (thin wrappers over tested `db/` functions; register each in `lib.rs`'s `generate_handler!`). TypeScript calls them only through typed wrappers in `src/api/` (`campaigns.ts`, `library.ts`), never raw `invoke` strings in components. JS passes camelCase args; Rust names are snake_case.
- **Library screen:** `src/components/library/LibraryScreen.tsx` is the generic UI any tool reuses: `<LibraryScreen library="<tool id>" title="..." itemTypes={[...]} />` gives folders, items (rename/move/tags/delete with undo), search and a Trash panel for the open campaign. See `src/modules/worldbuilding/` for the pattern (a module registers its tool + item types and renders `LibraryScreen`). Pure helpers (breadcrumbs, move menus, grouping tags) are in `library/helpers.ts` with Vitest tests. Destructive actions use `ConfirmButton` (two taps), since `window.confirm` is unreliable on Android WebViews. Not built yet: tag manager (rename/recolour/nest/delete tags), opening an item (editor arrives in Phase 4).
- **Links and backlinks** (`db/links.rs`, migration 0006): the `links` table is the single source of truth; backlinks are the reverse query. A link is (source item, target item, `source_ref`): `'manual'` for the item page's Links list now, later `'body'` for editor @mentions and `'field:<name>'` for link fields, so those write rows to the same table rather than a new mechanism. One-way, no self-links, both items live and in the same campaign, any tool to any tool. Removal is soft (row kept, `deleted_at` set; re-adding revives it). Trashing an item hides its links on both sides and restoring brings them back; purging removes them (`ON DELETE CASCADE`). Not built yet: `target_ref` (linking to a spot inside an item, e.g. a map pin; add the column when maps need it).
- **Item page and navigation:** `ItemView` (`src/components/item/`) is an item's page: tags, Links (with a `LinkPicker` that searches every tool), and "Linked from". Any screen opens an item with `useNavigation().openItem(id)` (`src/state/Navigation.tsx`); the shell keeps a stack so Back retraces links, keeps the tool mounted underneath (hidden) so its state survives, and clears the stack on campaign change. `itemDisplay.ts` has the icon/type/tool labels (via the registry). The document body/editor will live in `ItemView`. `ItemView` also has Rename, Tags (the same `TagEditor` as the library) and Delete (two-tap, goes to the trash; a trashed item's page shows "in the trash" with Restore and hides its editor). **Keeping lists fresh:** library screens stay mounted (hidden) behind an item page or another tab, so they would show stale data. Any code that changes library data from outside a library screen (item page edits, saving a roll...) must call `bumpDataVersion()` (`src/state/dataVersion.ts`); `LibraryScreen` reloads whenever that number changes. `LibraryScreen`'s own changes (create, rename, delete, restore, delete forever, tag...) also bump it after reloading itself, so the other screens that stay mounted behind it (the Cards Draw tab's list of decks in play, the formula list...) never keep showing things that are gone; any action that can find its target missing should bump it too, to refresh a stale list.
- **Document text** (`db/documents.rs`, migration 0007): a document is an `items` row with `item_type = 'document'`; its body is **Markdown text** in `document_content` (one row per item, same id, `ON DELETE CASCADE`; the item's trash state governs it). Markdown is the storage format so the Phase 4 rich editor (TipTap/BlockNote, both read/write Markdown) can replace the plain editor without converting data, and so content packs stay human-readable. `get_body`/`set_body` only work on live documents; saving bumps the item's `updated_at`; bodies over 2 MB are refused. Search now indexes the body too (name > tags > text in ranking); migration 0007 rebuilt the FTS table because FTS5 columns can't be altered. Not built yet: version history (spec: recent versions viewable/restorable), snippets/highlights in search results.
- **Rich document editor** (`src/lib/documents/`, `src/modules/worldbuilding/`; Phase 4 step 1): the stored body is still Markdown (decision: Markdown plus directive-style extensions for later block types such as callouts and secret blocks, not TipTap JSON). `markdownToDoc` / `docToMarkdown` (`markdown.ts`, `inline.ts`, pure, no editor needed) convert to and from TipTap's JSON (`types.ts`). **Promises, all tested** (`markdown.test.ts` examples + `markdown.property.test.ts`, thousands of random documents, random Markdown, and a separate inline-only random test): reading never throws and never drops text; what it does not understand (tables, HTML) is kept whole as a `rawMarkdown` block and written back unchanged; writing then reading gives the same document (after `normalizeDoc`, which drops empty paragraphs between blocks, trims line edges, and keeps emphasis off edge spaces); writing twice gives the same text. Single newlines inside a paragraph are real line breaks (the old plain editor stored text that way) and are written as backslash + newline. Italic is written `_x_` (so it can't merge with bold's `**`), or `*x*` when a letter touches it. **The writer checks itself:** `serializeInline` reads its own output back and, if it differs, tries a one-piece-at-a-time layout, then `<strong>/<em>/<del>` tags (the reader understands them); only if all fail is emphasis dropped (text is never lost; tests make sure it doesn't happen). Link marks are reduced to their `href` (TipTap adds `target`/`rel`; `sortMarks` strips them, a bug the unit tests missed and the browser check found). **When editing these files with scripts:** the Bash tool halves backslashes in heredocs and the Write tool writes CRLF; use the Edit tool for anything containing backslashes. UI: `DocumentEditor` (wrapper: load, autosave, "Edit as Markdown" toggle remembered per device in `deviceStorage`) holds either `RichEditor` (TipTap + StarterKit without underline, a formatting toolbar, link form with `normalizeLinkAddress`, a `/` menu built from `lib/documents/blockCommands.ts` via `@tiptap/suggestion`) or the old textarea. `RichEditor` converts to Markdown 300 ms after the last edit (it keeps the latest ProseMirror doc in a ref, so leaving/blur/hidden converts immediately and calls `onFlush`), then the autosaver adds its own 800 ms. A document is only rewritten when edited; opening one never changes it. **Tables and columns** (added after the first version): tables are real GFM tables (`| a | b |` + `| --- | --- |`; `lib/documents/tables.ts` splits rows and escapes cells: a pipe is `\|` even inside code, a line break in a cell is `<br>`, a cell holds one paragraph, the first row is always the header, short rows are padded to the header's width; alignment colons are accepted but not kept). A table row line needs an unescaped pipe, and a table can interrupt a paragraph. **Layout blocks are directives**: `::::columns` / `:::column` ... `:::` / `::::`, where an opening line has more colons than anything inside it (`fenceSize`), the closer is a colon-only line at least as long, and closers inside code fences are skipped. Unknown or unclosed-at-the-wrong-place directives are kept whole as `rawMarkdown`; a `:::column` outside `columns` is raw too; loose content directly inside `columns` goes into a column (`groupColumns`). Callouts, toggles and secret blocks should reuse this machinery (add a name in `parseBlocks`' directive branch and in `normalizeBlock`/`blockToLines`). The `/` menu and toolbar offer Table, 2 columns, 3 columns (`blockCommands.ts`; menu words can't contain spaces, so `/col`, not `/3 col`); inside a table or columns block a contextual bar offers add/delete row/column and "Remove columns" (`layoutNodes.ts`; cells are `paragraph+`, no merging). A floating toolbar (TipTap `BubbleMenu`) shows over a text selection (below it on touch screens, so it doesn't fight Android's own selection menu). Checks of "is the cursor inside X" use `insideNode` (an ancestor walk), not `editor.isActive`, which missed tables; checks for "text selection" use `"$cursor" in selection`, not `instanceof TextSelection` (the dev bundler can load two copies of the class). **Callouts, toggles, secret blocks** use the same directive machinery (`DIRECTIVES` in `markdown.ts` decides which node types need a longer fence): `:::callout [info|tip|warning|danger]` (an unknown kind is kept whole as raw Markdown, never changed), `:::toggle Inline **Markdown** title` (node `toggle` = `toggleSummary` + blocks; the title is one line, so line breaks in it become spaces; open/closed is editor-only state, not saved, and `RichEditor` skips reporting when only that changed), `:::secret [reveal-to note]` (attr `to`). **Secret blocks are only stored and labelled "GM only" so far; keeping them off players' devices is Phase 9's job** (strip them when sharing, per the "never sent" rule). The toolbar has an "Insert..." menu (callout, warning, toggle, secret, table, columns) so phones don't depend on typing `/`, and each block has a contextual bar (callout kind + remove, remove toggle, secret reveal-to + remove; "remove" keeps the content). **Mentions** (Phase 4 step 2; `lib/documents/mentions.ts`, `modules/worldbuilding/mentionNode.ts`, `PickerMenu.tsx`): typing `@` (after a space or at the start) searches the open campaign (every tool, never the document itself) and inserts a `mention` chip. **Stored as an ordinary Markdown link `[Name](item:<uuid>)`**, so it reads anywhere; the reader turns a link whose address is `item:<valid uuid>` into a `mention` node (an invalid id stays a normal link), and a mention can carry bold/italic/strike but never link/code marks (`cleanMention`). The label saved is the item's name when it was mentioned; **the editor shows the item's current name and icon** (looked up in batches, cached per editor, so a rename shows when the document is reopened; stale labels in the saved text are not rewritten, because opening a document must never change it). Chips for trashed or deleted items are struck through. Clicking a chip opens the item (`MentionSupport.open`, built in `DocumentEditor`; `RichEditor` works without support, `@` then does nothing). **Links:** `set_document_body(item_id, body, mentions)` saves the text and, in the same transaction, makes the document's `source_ref = 'body'` links exactly match the mentioned ids (`links::sync_source`; a mention of something gone, trashed, foreign or itself is skipped silently, other kinds of link are untouched). `DocumentEditor` computes `mentionIds(markdownToDoc(body))` on every save (code and raw blocks don't count) and bumps the data version only when the set changes; `ItemView` reloads on the data version and shows "mentioned in text" instead of Remove for links that exist only through the text (`list_manual_link_ids`). **Pack import rewrites `item:<old id>` to the new id inside document bodies** (`remapped_body`; ids outside the pack are left as written), and the exported `links` rows carry the body links. `PickerMenu`/`usePickerMenu` are the shared popup for the `/` and `@` menus (the `@` menu keeps matching across spaces because names have them; `allowSpaces`). Not built yet: mentions of a spot inside an item (a map pin; needs `target_ref`), refreshing stale saved labels, saved text styles, version history.
- **Fields** (Phase 4 step 3; `lib/fields/`, `db/fields.rs` + migration 0019, `api/fields.ts`, `components/fields/`): campaign-wide **definitions** (a name, a kind, a description, settings), reusable **field sets**, sets **applied** to an item, and **values** held by *any* item (documents, cards, maps...; cards keep their own value/notes for now). Seven kinds: text (single or multi-line), number (min/max/decimals/unit), bar (current/max; current may pass the limits for temporary points), dice formula (checked with the dice parser; the editor has a Roll button), dropdown (choices have stable ids, a name and an optional colour), list (entries with a title and a description), link (one or several items, optionally only one tool's library). **Dates and map locations are not here yet** (they need Phase 6's calendar and Phase 7's maps; add the kinds then). **The pure model is TypeScript and tested first** (`definition.ts` validation/repair/dropdown edits, `value.ts` `coerceValue` = the one gate every value passes through, `formatValue`, `indexValue`, `compareValues` with empties always last, `bar.ts`, `numberInput.ts`, `fieldSets.ts` `fieldsToShow`; random tests check coercion never throws and is stable); **Rust only stores and checks sizes, ownership and JSON** (`set_value` takes the value JSON plus the `ValueIndex` the TypeScript worked out: `sort_num`, `sort_text` (cut to 200 chars), `search_text`). Values are keyed by definition id, so renaming a field or a dropdown choice never disturbs saved values; **a field's kind never changes** (make a new one); live names are unique per campaign ignoring case (definitions and sets separately); definitions and sets are soft-deleted and restorable (`list_deleted_*`, shown in the Fields tab); deleting a field hides its values. When a dropdown's choices change the UI calls `refreshFieldValues` (re-indexes its values and clears ones whose choice was removed). **Link fields write rows into `links`** with `source_ref = 'field:<field id>'` in the same transaction as the value (`links::sync_source`, like mentions; deleting the field hides those links and restoring brings back exactly those, matched by the deletion timestamp). The item page's Links list says "from text or a field" for links that aren't hand-made. A value has a `secret` mark (GM-only; stored and shown now, kept off players' devices by Phase 9). **Content packs** carry `field_definitions`, `field_sets`, `field_set_members`, `item_field_sets`, `field_values` (all optional, still format 1): import makes new ids, rewrites a link field's value ids and the `field:` ref of its links (only link fields' values are ever rewritten), renames clashing names with " (2)", and skips what doesn't hold together. UI: Worldbuilding has **Documents** and **Fields** tabs (`FieldsManager`: make/change/delete fields and sets); every item's page has a **Fields** panel (`ItemFieldsPanel`: add a set or a single field, edit values, GM-only toggle, Clear). Values are committed on blur/Enter (never while typing) and show why they don't fit. Search over field values is not wired in yet: `search_text` is stored and indexed for the global-search/query step. Not built yet: templates (apply a set plus starter text), queries, field views, entity slots and `[A.Field]` references, per-field defaults.
- **Item editors via the registry:** an `ItemTypeDefinition` can have an optional `editor` component (`{ itemId }` prop); `ItemView` renders whatever the item's type registered, so core code never mentions documents. Worldbuilding registers `DocumentEditor` (plain textarea) in `modules/worldbuilding/documentType.ts`; maps/decks will bring their own the same way.
- **Autosave** (`src/lib/autosave.ts`, tested): `createAutosaver({save, delayMs, onStatus})` debounces edits (800 ms in the editor), runs saves one at a time in order, keeps unsaved text if a save fails (retried on next flush), and `flush()` never rejects. The editor flushes on blur, on unmount and on `visibilitychange` to hidden (Android may kill hidden apps). Reuse it for any text-like editor. Note: `tsconfig` targets ES2020, so avoid newer array methods like `.at()`.
- **Content packs** (`src-tauri/src/pack/`, migration 0008): a `.ttrpgpack` file is a zip with `manifest.json` (`format: "ttrpg-toolkit-pack"`, `formatVersion`, `packId`, app/schema versions, campaign name, counts) plus `data/{folders,items,tags,item_tags,links,documents}.json` (and a reserved `assets/`). The JSON records in `pack/format.rs` are deliberately separate from the DB structs, so DB changes never silently change the file format. **Export** (`export.rs`) writes one whole campaign including trashed rows. **Import** (`import.rs`) *always creates a new campaign* "<name> (imported)" with fresh ids (never overwrites), in one transaction (all-or-nothing); items keep `origin_pack_id`/`origin_item_id` for a future "update from original". Reading is separate from writing: `read_pack` enforces size limits (zip-bomb guard), refuses non-packs and packs from a newer `formatVersion`, and *repairs and reports* inconsistent data as warnings (dangling references dropped, parent loops broken, clashing tag names renamed, parents ordered before children). Unknown files/fields are ignored; missing data files count as empty. **Evolving the format:** optional new fields are not breaking (use `#[serde(default)]`); a breaking change bumps `FORMAT_VERSION`, adds an upgrade step in `parse_manifest`, and adds a NEW golden file (`src-tauri/tests/fixtures/pack_v2...`). **Never edit or regenerate `pack_v1.ttrpgpack`**: the `the_committed_version_1_pack_still_imports` test is the promise that old packs keep importing. To add a new kind of data to packs: add its record type and file to `format.rs`, export it, sanitize + import it, extend `populate`/`snapshot` in `pack/tests.rs`. **Ids inside opaque JSON are remapped on import:** saved draws (`result_json`) and decks in play (`state_json`, `source_id`) remember cards by item id, and import gives every item a new id, so `import.rs` rewrites every string that equals an old item id (`remapped_json`; text with nothing to replace is stored byte-for-byte as it was; ids not in the pack, e.g. deleted cards, are left alone and a game's `source_id` becomes null if its source wasn't in the pack). Anything new that stores item ids inside JSON must go through the same rewrite. Files travel to/from Rust as **base64 text** (`src/lib/base64.ts` in JS, `pack::encode_for_transport`/`decode_from_transport` in Rust), never raw bytes. **Android gotcha:** Tauri never delivers a raw request body to commands on Android (`InvokeBody::Raw` is unsupported there; it always sends JSON), so a command taking raw bytes works on Windows and fails on the phone. Any command that moves a file or other binary data must use the text transport; there is one code path for all platforms so tests on Windows cover what the phone runs. JS saves/opens files with the Tauri dialog + fs plugins (verified on Android: content URIs work, `.ttrpgpack` names are kept). The pack commands are `async` so big packs don't freeze the window. UI: Export on each campaign row, "Import pack..." with a preview step on the Campaigns screen. Not built yet: importing selected items into an existing campaign, "bring linked items along", "update from original", assets, rulesets.
- **Command palette** (`components/palette/CommandPalette.tsx`): opened with Ctrl/Cmd+K or the status bar's Search button (the way in on Android). Lists `registry.getCommands()` filtered/ranked by `matchCommands` (`src/lib/palette.ts`, tested) plus matching items from the open campaign (`searchItems`, any tool); choosing an item calls `openItem`, a command runs with `{ openTool }`. To add a palette entry, register a `CommandDefinition` in a module; don't edit the palette. Not built yet: quick-create actions, rolling dice, switching campaigns from the palette, per-command shortcuts.
- **Dice engine** (`src/lib/dice/`, pure TypeScript, Vitest; Phase 2): `parseDice(text)` returns `{ok, expression}` or `{ok:false, error:{message, position}}` and never throws; `rollDice(expression, rng)` / `rollNotation(text, rng)` return a `DiceResult` recording every die (`kept`, `exploded`, `fromExplosion`, `rerolledFrom`, pool `success`), per-term subtotals and `capped`. Everything random goes through the `Rng` interface (`rng.ts`: `createRng(seed)` is a seeded mulberry32; `newSeed()` is the only `Math.random` use), so tests script dice with `testing.ts`'s `scripted(...)` and a result can be reproduced from its seed. Notation: `2d6+3`, `4d6kh3`/`kl`/`dh`/`dl`, `d20 adv`/`dis` (= `2d20kh1`/`kl1`, single die only), `!` explode (default top face, or `!>=9`), `r1` reroll until it stops matching / `ro1` once (Roll20 style), pools `6d10>=8`, `4dF`. Modifier order is fixed: reroll, explode, keep/drop, target. Limits: 100 dice per formula (total), 100 faces, 100 explosions and 100 rerolls per die (hitting the last two sets `capped`). Roll order for seeding: per die, first roll, rerolls, then explosions. `rerollDice(expression, previous, lockedTermIndexes, rng)` rolls again keeping locked terms exactly (locking is per term, e.g. keep the `1d20` and reroll the `+1d6`, not per die). Not built: `* / ()`, custom dice (Phase 5 rulesets).
- **Results and roll log** (`src/lib/results/`, Phase 2): `formatDiceResult` writes a result as one line (`4d6kh3 → [(2), 6, 3, 5] = 14`: round brackets = dropped, `!` = exploded, `✓` = success, `(was 1)` = rerolled); `termTexts` gives each term separately. `createRollLog()` (`rollLog.ts`) is an in-memory, newest-first store (200 entries) with `roll`, `reroll` (adds a NEW entry on top, carrying the locks), `toggleLock`, `markSaved`, `clear`, `subscribe` and a stable `entries()` array for React's `useSyncExternalStore`. The app has one instance, `src/state/rollLog.ts` (`rollLog`, `useRollLog()`); it is **never persisted** (cleared on restart, and on campaign change in `App.tsx`). A roll worth keeping is *saved* as a library item. `RollLogEntry` is a union on `kind` (`DiceLogEntry` | `DrawLogEntry`, both with `id`, `seed`, `label`, `text`, `savedItemId`); `entries("dice"|"draw"|"all")` is typed per kind. Tables and generators will add their own kind, formatter and entry type the same way. Lock/reroll is dice-only (`reroll`/`toggleLock` ignore draws). The UI for a result is `components/results/LogEntryView.tsx` (one entry, any kind: roll/draw again, copy, save) and `RollLogList.tsx` (list + kind filter + clear); the Dice tool's roll log has an All/Dice/Card draws filter.
