# TTRPG Toolkit

A personal, local-first, system-agnostic TTRPG toolkit for Windows and Android, shared with a small group of friends and built in nine phases. **Current phase: Phases 1 to 3 are complete. Phase 4 (worldbuilding) is built; Katie asked for a UI redesign pass first ("Phase 4b", stages 1 to 7 done, stage 8 (smart-chip generator editor) is next; see "Phase 4b: status and handoff" below). She tests everything once, on Windows and Android, after the whole of 4b, then says "commit please". Phase 5 (rulesets and encounters) comes after that, in a new chat.** Phase 2 delivered: the whole Dice side (parser/roller, roll log, saved rolls, formulas, quick buttons), the Cards library (cards with pictures, sets, decks, pools), card draws with saved draws, decks in play, spreads, starter decks (playing cards, Tarokka), and the widget framework with the quick tools panel. Phase 3 delivered: random tables (weights and ranges, slots that roll dice, other tables and card draws, labels, unique picks, avoid-recent, entry tags), a slot-chip entry editor, rename-with-slot-update, the name generator (one tool drawing from chosen tables, with a tag filter and saved presets), content-pack support for all of it, quick widgets, and four starter sets of tables (fantasy names, tavern names, quirks and rumors, weather).

The full spec is [spec.md](spec.md). This file is a summary; when the two disagree, the spec wins (and tell Katie so the spec can be updated).

## Architecture in brief

- **Eight tools, each with its own library** (folders, tags, search): Worldbuilding (documents), Cards, Tables and generators, Maps, Calendar and timeline, Encounters, Dice, GM screen.
- **Five shared engines** underneath: fields, queries, results (dice/tables/draws/generators + roll log), project state, and links/tags. Tools plug into the engines instead of reimplementing them.
- **Module registry:** each module registers its tools, item types, embed types, field types, table slot types, widgets, command palette actions and content pack data. The core app picks them up automatically. New features should plug in here, not rewire the core.
- **Content packs:** one zip format (versioned) for backups, copying between projects and sharing.
- **Rulesets** are global; everything else lives in a project.

## Rules that come from the spec's principles

- **Local first, offline always.** Sync is an extra, never a requirement.
- **Every record has a UUID, timestamps and a soft-delete flag.** Never hard-delete library items; deleted items go to the trash with restore.
- **Schema is versioned with step-by-step migrations.** Migrations are append-only; never edit one that has shipped. Content packs carry a version too.
- **Data, not code,** for system-specific things (rulesets, dice, stat blocks, tables, templates).
- **Simple by default, deep on demand.** Advanced options go behind an "Advanced" toggle.
- **Secret content is never sent to a player's device,** not just hidden in the UI.
- **No outside apps required.** Imports are optional.
- Engines are *designed* in Phase 1 but *built* only when the first tool needs them. Keep the foundation small.

## Conventions

*Proposed at project start; edit freely.*

- TypeScript `strict` on; no `any` (use `unknown` and narrow).
- React function components and hooks only.
- npm is the package manager.
- Logic with tricky rules (dice parser, draw rules, calendar math, pathfinding, migrations) gets automated tests. Logic written in Rust is tested with `cargo test` (in `#[cfg(test)]` modules, using in-memory SQLite); logic written in TypeScript uses Vitest (`*.test.ts` next to the code). UI is checked by running the app.
- **Database lives in Rust** (`rusqlite`, bundled SQLite) in `src-tauri/src/db/`. React never touches SQL; it calls Tauri commands. The DB file is `toolkit.db` in the app data dir.
- **Migrations:** numbered `.sql` files in `src-tauri/migrations/`, registered in `src-tauri/src/db/migrations.rs`. Version is tracked in SQLite's `user_version`. To change the schema, add the next numbered file and entry; never edit an existing one.
- **Module registry** (`src/registry/`): a module is a `ModuleDefinition` object (id plus optional `tools`, `itemTypes`, `commands`, `widgets`; types in `registry/types.ts`). To add a feature: create `src/modules/<name>/index.ts` exporting a module, then add it to the list in `src/registry/index.ts`. The app shell (`App.tsx`) builds its navigation from `registry.getTools()`; the command palette will read `registry.getCommands()`. Core code must never import a specific module's screens directly. New contribution kinds (embed types, field types, widgets...) are added to the registry when the first feature needs them. Duplicate ids throw at startup.
- **Projects (formerly "campaigns"; Phase 4b stage 1, migration 0024):** the word is *project* everywhere in code, database (`projects` table, `project_id` columns, setting `current_project_id`), commands (`list_projects`...) and screens (a project is like a LegendKeeper project or Notion workspace). **What deliberately still says "campaign":** the old migrations 0001-0023 (append-only; 0024 renames the table and columns), the **content-pack manifest key `"campaign"`** (`pack/format.rs` maps it with `#[serde(rename)]`, so `pack_v1.ttrpgpack` and every pack already exported still import), and tests that build old-schema databases (`migrations.rs`, `search.rs`). Per-device `localStorage` keys (`ttrpg.rollContext.<project id>`) hold ids, not words, so they were not renamed.
- **Properties and Filter sets (Phase 4b stage 2):** what the code calls a *field* is called a **property** on every screen and in every message (code names `field`, `FieldDefinition`, `field_values`, the `[A.Faction]` slot syntax and the pack files do not change); a field set is a **property set**; a smart collection is a **filter set** (item type id stays `smart_collection`; `creatable: false`, so it is not in the Worldbuilding "New item" list). **Properties are managed on the page, there is no Fields tab:** `ItemFieldsPanel` has "Add a property set", "Add a property", **New property** (`FieldDefinitionForm`; `onDone(savedId)` adds the new one to the page), a `⋯` menu per property (Edit property; Delete property = project-wide, two taps, says every page loses it), and a "Deleted properties" list with Restore. **On a template page** the panel also has New property set, Edit set and Delete set (`FieldSetForm`; a set made there is applied to the template), because a template decides which sets new documents get; deleted sets can be restored there too. `FieldsManager.tsx` was removed. **Filter sets** are made in the Worldbuilding **Filter sets** tab (`FilterSets.tsx`, a temporary home until the Stage 4 sidebar has a "Filter sets" entry) and from a card pool's Add picker ("New filter set" makes one, adds it to the pool and opens it); `createFilterSet` is the shared helper. `LibraryScreen` has `showTitle` (Worldbuilding turns it off: no big heading, and the root crumb "All pages" only shows inside a folder). Rust error messages and warnings use the new words too.
- **App shell** (Phase 4b stage 4; `App.tsx`, `components/shell/`): a **fixed left sidebar** (a slide-in drawer under 700 px, opened by the ☰ button in a slim top bar; it closes after you pick something) holds, top to bottom: the **project switcher** (`ProjectSwitcher`; "Manage projects…" opens the Projects screen), the **search bar** (`SidebarSearch`), then a **row of tool icons** (icon only, with a label as tooltip and `aria-label`: Home, Cards, Dice, Tables) from `registry.getTools()` (`inSidebar: false` leaves one out, as for Projects; `placement: "bottom"` puts the icon in the **footer at the bottom of the sidebar** instead: Trash and Settings), with whatever a tool's `sidebar: Component` draws (Home's pages tree and Templates) under the row. **Settings** is a placeholder screen ("coming in a later update"); Katie will design it later. There is **no Worldbuilding screen**: the **Home** tool (module `worldbuilding`, library id still `worldbuilding`, shown to people as "Pages" via `ToolDefinition.libraryLabels` and `registry.getLibraryLabel`, which every place that names a library must use) carries the **pages tree** (`WorldbuildingTree.tsx`: documents only, folders open and close and load their documents when opened, "+ Page" and "+ Folder", a "+" per folder, a **⋯ menu on each folder and page for Rename (pages go through the rename review), Move and Delete** with an Undo link, no drag and drop yet) and a **Templates** section (collapsible, **collapsed by default**, the header shows the count; every template flat, "+ Template", a "+" per template that makes a page from it, and the starter templates when there are none). Home's own screen is a placeholder until Phase 8 dashboards. A **Trash** tool (`PagesTrash`) restores or purges deleted pages, folders, templates and filter sets; the other tools keep their own library trash. **Filter sets are not in the sidebar** (Katie: only for searches): they are found by search and made from a card pool's Add picker (`modules/worldbuilding/filterSets.ts`); the Filter sets tab and `FilterSets.tsx` were removed. **Quick tools float at the bottom right** (`QuickMenu`: one round icon per registered widget, dice, cards, table; hidden on a phone while a panel is open). A page has a header: breadcrumb, big icon + title, type and tag chips, Rename / Tags / Delete, tab strip (`ItemPage`). **Phase 6's date, session, weather and location** go near the project switcher or in the page header. **Dev preview:** `npm run dev` in a plain browser uses `src/dev/mockBackend.ts`.
- **Library items:** every item of every tool is a row in the shared `items` table (`library` = owning tool id, `item_type`, `folder_id`, `visibility` of `default|visible|secret`). Types needing more data get their own detail table keyed by the same id. Tags, links, search and trash work on `items`, so they work for every tool. Folders (`folders` table, nestable) belong to one tool's `library`; an item and its folder must share project and library. Data-layer code is in `src-tauri/src/db/{items,folders}.rs`; all errors use the shared `DbError` (`db/error.rs`).
- **Trash semantics:** deleting a folder soft-deletes its subfolders and items with the *same* `deleted_at`, so restoring the folder restores only that group (things deleted earlier stay deleted). `db/trash.rs` lists "roots of deletion" only, restores items/folders (falling back to the top level if the original parent is still trashed), and permanently deletes (`purge_*`, `empty` with an optional "older than" cutoff). Only trashed rows can be purged. Any table that references `items` (links...) must use `ON DELETE CASCADE` so purging works.
- **Tags** (`db/tags.rs`, migration 0003): project-wide, optional `#rrggbb` colour, nestable (loops refused), unique among live siblings ignoring case (checked in code and by a unique index). Soft-deleted with their sub-tags under one shared timestamp; restore mirrors folders and refuses a name clash. `item_tags` links carry timestamps and `deleted_at` (a removed link is kept, so removals can sync later; re-adding revives it). `tags::items_with_tag(.., include_subtags)` finds items by tag. Tags can only attach to live items/tags in the same project.
- **Tauri commands** all live in `src-tauri/src/commands.rs` (thin wrappers over tested `db/` functions; register each in `lib.rs`'s `generate_handler!`). TypeScript calls them only through typed wrappers in `src/api/` (`projects.ts`, `library.ts`), never raw `invoke` strings in components. JS passes camelCase args; Rust names are snake_case.
- **Library screen:** `src/components/library/LibraryScreen.tsx` is the generic UI any tool reuses: `<LibraryScreen library="<tool id>" title="..." itemTypes={[...]} />` gives folders, items (rename/move/tags/delete with undo), search and a Trash panel for the open project. See `src/modules/worldbuilding/` for the pattern (a module registers its tool + item types and renders `LibraryScreen`). Pure helpers (breadcrumbs, move menus, grouping tags) are in `library/helpers.ts` with Vitest tests. Destructive actions use `ConfirmButton` (two taps), since `window.confirm` is unreliable on Android WebViews. Not built yet: tag manager (rename/recolour/nest/delete tags), opening an item (editor arrives in Phase 4).
- **Links and backlinks** (`db/links.rs`, migration 0006): the `links` table is the single source of truth; backlinks are the reverse query. A link is (source item, target item, `source_ref`): `'manual'` for the item page's Links list now, later `'body'` for editor @mentions and `'field:<name>'` for link fields, so those write rows to the same table rather than a new mechanism. One-way, no self-links, both items live and in the same project, any tool to any tool. Removal is soft (row kept, `deleted_at` set; re-adding revives it). Trashing an item hides its links on both sides and restoring brings them back; purging removes them (`ON DELETE CASCADE`). Not built yet: `target_ref` (linking to a spot inside an item, e.g. a map pin; add the column when maps need it).
- **Item page and navigation:** `ItemView` (`src/components/item/`) is an item's page: tags, Links (with a `LinkPicker` that searches every tool), and "Linked from". Any screen opens an item with `useNavigation().openItem(id)` (`src/state/Navigation.tsx`); the shell keeps a stack so Back retraces links, keeps the tool mounted underneath (hidden) so its state survives, and clears the stack on project change. `itemDisplay.ts` has the icon/type/tool labels (via the registry). The document body/editor will live in `ItemView`. `ItemView` also has Rename, Tags (the same `TagEditor` as the library) and Delete (two-tap, goes to the trash; a trashed item's page shows "in the trash" with Restore and hides its editor). **Keeping lists fresh:** library screens stay mounted (hidden) behind an item page or another tab, so they would show stale data. Any code that changes library data from outside a library screen (item page edits, saving a roll...) must call `bumpDataVersion()` (`src/state/dataVersion.ts`); `LibraryScreen` reloads whenever that number changes. `LibraryScreen`'s own changes (create, rename, delete, restore, delete forever, tag...) also bump it after reloading itself, so the other screens that stay mounted behind it (the Cards Draw tab's list of decks in play, the formula list...) never keep showing things that are gone; any action that can find its target missing should bump it too, to refresh a stale list.
- **Document text** (`db/documents.rs`, migration 0007): a document is an `items` row with `item_type = 'document'`; its body is **Markdown text** in `document_content` (one row per item, same id, `ON DELETE CASCADE`; the item's trash state governs it). Markdown is the storage format so the Phase 4 rich editor (TipTap/BlockNote, both read/write Markdown) can replace the plain editor without converting data, and so content packs stay human-readable. `get_body`/`set_body` only work on live documents; saving bumps the item's `updated_at`; bodies over 2 MB are refused. Search now indexes the body too (name > tags > text in ranking); migration 0007 rebuilt the FTS table because FTS5 columns can't be altered. Not built yet: version history (spec: recent versions viewable/restorable), snippets/highlights in search results.
- **Rich document editor** (`src/lib/documents/`, `src/modules/worldbuilding/`; Phase 4 step 1): the stored body is still Markdown (decision: Markdown plus directive-style extensions for later block types such as callouts and secret blocks, not TipTap JSON). `markdownToDoc` / `docToMarkdown` (`markdown.ts`, `inline.ts`, pure, no editor needed) convert to and from TipTap's JSON (`types.ts`). **Promises, all tested** (`markdown.test.ts` examples + `markdown.property.test.ts`, thousands of random documents, random Markdown, and a separate inline-only random test): reading never throws and never drops text; what it does not understand (tables, HTML) is kept whole as a `rawMarkdown` block and written back unchanged; writing then reading gives the same document (after `normalizeDoc`, which drops empty paragraphs between blocks, trims line edges, and keeps emphasis off edge spaces); writing twice gives the same text. Single newlines inside a paragraph are real line breaks (the old plain editor stored text that way) and are written as backslash + newline. Italic is written `_x_` (so it can't merge with bold's `**`), or `*x*` when a letter touches it. **The writer checks itself:** `serializeInline` reads its own output back and, if it differs, tries a one-piece-at-a-time layout, then `<strong>/<em>/<del>` tags (the reader understands them); only if all fail is emphasis dropped (text is never lost; tests make sure it doesn't happen). Link marks are reduced to their `href` (TipTap adds `target`/`rel`; `sortMarks` strips them, a bug the unit tests missed and the browser check found). **When editing these files with scripts:** the Bash tool halves backslashes in heredocs and the Write tool writes CRLF; use the Edit tool for anything containing backslashes. UI: `DocumentEditor` (wrapper: load, autosave, "Edit as Markdown" toggle remembered per device in `deviceStorage`) holds either `RichEditor` (TipTap + StarterKit without underline, a formatting toolbar, link form with `normalizeLinkAddress`, a `/` menu built from `lib/documents/blockCommands.ts` via `@tiptap/suggestion`) or the old textarea. `RichEditor` converts to Markdown 300 ms after the last edit (it keeps the latest ProseMirror doc in a ref, so leaving/blur/hidden converts immediately and calls `onFlush`), then the autosaver adds its own 800 ms. A document is only rewritten when edited; opening one never changes it. **Tables and columns** (added after the first version): tables are real GFM tables (`| a | b |` + `| --- | --- |`; `lib/documents/tables.ts` splits rows and escapes cells: a pipe is `\|` even inside code, a line break in a cell is `<br>`, a cell holds one paragraph, the first row is always the header, short rows are padded to the header's width; alignment colons are accepted but not kept). A table row line needs an unescaped pipe, and a table can interrupt a paragraph. **Layout blocks are directives**: `::::columns` / `:::column` ... `:::` / `::::`, where an opening line has more colons than anything inside it (`fenceSize`), the closer is a colon-only line at least as long, and closers inside code fences are skipped. Unknown or unclosed-at-the-wrong-place directives are kept whole as `rawMarkdown`; a `:::column` outside `columns` is raw too; loose content directly inside `columns` goes into a column (`groupColumns`). Callouts, toggles and secret blocks should reuse this machinery (add a name in `parseBlocks`' directive branch and in `normalizeBlock`/`blockToLines`). The `/` menu and toolbar offer Table, 2 columns, 3 columns (`blockCommands.ts`; menu words can't contain spaces, so `/col`, not `/3 col`); inside a table or columns block a contextual bar offers add/delete row/column and "Remove columns" (`layoutNodes.ts`; cells are `paragraph+`, no merging). A floating toolbar (TipTap `BubbleMenu`) shows over a text selection (below it on touch screens, so it doesn't fight Android's own selection menu). Checks of "is the cursor inside X" use `insideNode` (an ancestor walk), not `editor.isActive`, which missed tables; checks for "text selection" use `"$cursor" in selection`, not `instanceof TextSelection` (the dev bundler can load two copies of the class). **Callouts, toggles, secret blocks** use the same directive machinery (`DIRECTIVES` in `markdown.ts` decides which node types need a longer fence): `:::callout [info|tip|warning|danger]` (an unknown kind is kept whole as raw Markdown, never changed), `:::toggle Inline **Markdown** title` (node `toggle` = `toggleSummary` + blocks; the title is one line, so line breaks in it become spaces; open/closed is editor-only state, not saved, and `RichEditor` skips reporting when only that changed), `:::secret [reveal-to note]` (attr `to`). **Secret blocks are only stored and labelled "GM only" so far; keeping them off players' devices is Phase 9's job** (strip them when sharing, per the "never sent" rule). The toolbar has an "Insert..." menu (callout, warning, toggle, secret, table, columns) so phones don't depend on typing `/`, and each block has a contextual bar (callout kind + remove, remove toggle, secret reveal-to + remove; "remove" keeps the content). **Mentions** (Phase 4 step 2; `lib/documents/mentions.ts`, `modules/worldbuilding/mentionNode.ts`, `PickerMenu.tsx`): typing `@` (after a space or at the start) searches the open project (every tool, never the document itself) and inserts a `mention` chip. **Stored as an ordinary Markdown link `[Name](item:<uuid>)`**, so it reads anywhere; the reader turns a link whose address is `item:<valid uuid>` into a `mention` node (an invalid id stays a normal link), and a mention can carry bold/italic/strike but never link/code marks (`cleanMention`). The label saved is the item's name when it was mentioned; **the editor shows the item's current name and icon** (looked up in batches, cached per editor, so a rename shows when the document is reopened; stale labels in the saved text are not rewritten, because opening a document must never change it). Chips for trashed or deleted items are struck through. Clicking a chip opens the item (`MentionSupport.open`, built in `DocumentEditor`; `RichEditor` works without support, `@` then does nothing). **Links:** `set_document_body(item_id, body, mentions)` saves the text and, in the same transaction, makes the document's `source_ref = 'body'` links exactly match the mentioned ids (`links::sync_source`; a mention of something gone, trashed, foreign or itself is skipped silently, other kinds of link are untouched). `DocumentEditor` computes `mentionIds(markdownToDoc(body))` on every save (code and raw blocks don't count) and bumps the data version only when the set changes; `ItemView` reloads on the data version and shows "mentioned in text" instead of Remove for links that exist only through the text (`list_manual_link_ids`). **Pack import rewrites `item:<old id>` to the new id inside document bodies** (`remapped_body`; ids outside the pack are left as written), and the exported `links` rows carry the body links. `PickerMenu`/`usePickerMenu` are the shared popup for the `/` and `@` menus (the `@` menu keeps matching across spaces because names have them; `allowSpaces`). Not built yet: mentions of a spot inside an item (a map pin; needs `target_ref`), refreshing stale saved labels, saved text styles, version history.
- **Fields** (Phase 4 step 3; `lib/fields/`, `db/fields.rs` + migration 0019, `api/fields.ts`, `components/fields/`): project-wide **definitions** (a name, a kind, a description, settings), reusable **field sets**, sets **applied** to an item, and **values** held by *any* item (documents, cards, maps...; cards keep their own value/notes for now). Seven kinds: text (single or multi-line), number (min/max/decimals/unit), bar (current/max; current may pass the limits for temporary points), dice formula (checked with the dice parser; the editor has a Roll button), dropdown (choices have stable ids, a name and an optional colour), list (entries with a title and a description), link (one or several items, optionally only one tool's library). **Dates and map locations are not here yet** (they need Phase 6's calendar and Phase 7's maps; add the kinds then). **The pure model is TypeScript and tested first** (`definition.ts` validation/repair/dropdown edits, `value.ts` `coerceValue` = the one gate every value passes through, `formatValue`, `indexValue`, `compareValues` with empties always last, `bar.ts`, `numberInput.ts`, `fieldSets.ts` `fieldsToShow`; random tests check coercion never throws and is stable); **Rust only stores and checks sizes, ownership and JSON** (`set_value` takes the value JSON plus the `ValueIndex` the TypeScript worked out: `sort_num`, `sort_text` (cut to 200 chars), `search_text`). Values are keyed by definition id, so renaming a field or a dropdown choice never disturbs saved values; **a field's kind never changes** (make a new one); live names are unique per project ignoring case (definitions and sets separately); definitions and sets are soft-deleted and restorable (`list_deleted_*`, shown in the Fields tab); deleting a field hides its values. When a dropdown's choices change the UI calls `refreshFieldValues` (re-indexes its values and clears ones whose choice was removed). **Link fields write rows into `links`** with `source_ref = 'field:<field id>'` in the same transaction as the value (`links::sync_source`, like mentions; deleting the field hides those links and restoring brings back exactly those, matched by the deletion timestamp). The item page's Links list says "from text or a field" for links that aren't hand-made. A value has a `secret` mark (GM-only; stored and shown now, kept off players' devices by Phase 9). **Content packs** carry `field_definitions`, `field_sets`, `field_set_members`, `item_field_sets`, `field_values` (all optional, still format 1): import makes new ids, rewrites a link field's value ids and the `field:` ref of its links (only link fields' values are ever rewritten), renames clashing names with " (2)", and skips what doesn't hold together. UI: Worldbuilding has **Documents** and **Fields** tabs (`FieldsManager`: make/change/delete fields and sets); every item's page has a **Fields** panel (`ItemFieldsPanel`: add a set or a single field, edit values, GM-only toggle, Clear). Values are committed on blur/Enter (never while typing) and show why they don't fit. Search over field values and queries are built (see Queries and smart collections). Not built yet: per-field defaults, dates and map locations.
- **Templates** (Phase 4 step 4; `db/templates.rs`, `db/template_starters.rs`, `lib/templates/starterTemplates.ts`, `src/starter/templates/`): **a template is a library item** (library `worldbuilding`, type `template`, icon 📋) set up like a document, with no storage of its own: its **text** is the starter text (`documents::holds_text` lets templates hold a body; pack import accepts it), the **field sets applied to it** are the sets a new document gets, the **values it holds** are the defaults (GM-only marks included), and its **tags** are the tags the new document gets. `templates::create_from(template, name, folder)` copies all of that (plus the links its mentions and link-field defaults make, and the icon) into a new `document` in **one transaction**; deleted tags/sets/fields and cleared values are not copied. **Copy semantics, decided by Katie:** the new document does not remember its template, so editing a template later never changes documents made from it; **templates apply to new documents only** (no "apply to an existing document"); the folder is chosen when the document is made (not part of a template). Folder-aware suggestions (an NPCs folder offers the NPC template) were deferred to the quick-create button. Not built yet: nested-document tabs and embed slots in templates (they arrive with the child-document step). UI: the Worldbuilding library has **New from template…** (`NewFromTemplate`, via `LibraryScreen`'s new `extraCreate` slot that gets the current folder): pick a template, name it (blank = "New <template>"), and it opens; a template's page shows a short hint above the same editor, and the usual Fields and Tags sections below are how its sets, defaults and tags are set up. `list_items_of_type` lists every template across folders. **Starter templates** follow the starter decks and tables: `TemplateStarterDef` (pure data) -> `toTemplateBundle` -> `install_template_bundle` -> `template_starters::install` (one transaction, folder "Templates", items carry `origin_pack_id = 'starter:templates'`, so "already added" is known; refuses if a template of one of the names exists or a same-named field has another kind). **Fields and field sets that already exist by name are used as they are**, not duplicated or changed; tags are reused. One set is installed: NPC, Location, Faction, Item, Quest and Session (31 fields, 6 sets, 6 tags, all original text; no default values and no links, so they work in any project; dropdown choice ids are `choiceId(label)`). To add starters: write a def, list it in `src/starter/templates/index.ts`; `starterTemplates.test.ts` checks every one (valid fields, sets use only its fields, text is exactly what the editor would write, tags and sets resolve). **A golden file ties the two languages together:** the TypeScript test writes/compares `src-tauri/tests/fixtures/starter_templates_core.json` (`npx vitest run -u src/lib/templates` after changing the starters), and a Rust test installs that exact file. Not built yet: templates for other tools.
- **Page tabs** (Phase 4 step 5; migration 0020, `db/tabs.rs`, `api/tabs.ts`, `components/item/`): **a page works like a LegendKeeper page** (Katie's choice): one page, the title, type, tags and Rename/Tags/Delete stay put, a **tab strip** under them (Main | each tab | ＋) switches the content below. - **Queries and smart collections** (Phase 4 step 6; migrations 0021 and 0022; TS `src/lib/queries/`, Rust `db/query.rs` + `query_tests.rs`, `db/smart_collections.rs`; UI `components/queries/`): a **query** is plain data, stored as JSON and read by both sides: `{version: 1, where: Group, sort: SortKey[]}`; a **Group** is `{op: "all"|"any", not, rules: (Rule|Group)[]}` (nested at most 4 deep, 100 rules, 50 ids per list, text <= 200 chars) and a **Rule** is `{kind, ...parts, not}`: `itemType`, `library` (the tool), `folder` (+ subfolders), `tag` (+ sub-tags), `name` (contains), `text` (appears in the name, a document's body or any field's text), `field` (with a **test** per field kind: contains/equals for text, formula and list; number/between for number and bar (a bar uses its current value); choice for dropdown; links for a link field; empty for any; `testsForKind`), `linksTo`, `linkedFrom`, `changed` (in the last N days). Sort: name, created, updated, type or a field (up to 3 keys; items without a value come last either way; ties fall back to the name). **Shared meaning (kept identical on both sides):** an **incomplete** rule (nothing chosen, empty text) and an **empty group** are *ignored* (so a query being built finds everything, never nothing); a rule naming a deleted tag, folder or field, or a test that doesn't suit the field's kind, *matches nothing* (and its "not" matches everything), so a deleted tag never silently widens a collection; trashed items and tab children (`item_tabs.child_id`) are never in an answer; text tests ignore case for all of Unicode (the `tt_fold` SQL function, registered on every connection in `db::init`; rusqlite's `functions` feature); a link field is tested through the `links` table (`field:<id>`). **TS owns the shape and the repair**: `normalizeQuery` is the one gate (never throws; refuses an unknown rule or a newer version with a sentence instead of guessing; `parseQuery` for stored text); `lib/queries/build.ts` edits a query immutably by path; `describe.ts` writes it in words. **Rust** re-validates and turns it into **one parameterized SQL statement** (`query::run`; typed text is only ever a parameter; at most 5,000 results, `truncated` says when there were more; `only_type` lets a pool ask for cards). The tests: a golden file `src-tauri/tests/fixtures/queries.json` (written by a Vitest snapshot, read and written back by a Rust test), property tests on the TS side, and a Rust test that compares the SQL with a slow independent evaluator over thousands of random queries on random projects (planting a bug in the SQL makes it fail). **Smart collections** are `items` rows (library `worldbuilding`, type `smart_collection`, icon 🔎, made from the library's "New item" form) with a `smart_collections` detail row (`query_json`; no row yet reads as the empty query; saving validates it and keeps the old one if refused). They are *live*: the answer is computed each time it is opened. Commands: `run_query` (an unsaved query, for the live preview), `get_smart_collection`, `set_smart_collection_query`, `run_smart_collection`; TS wrappers in `api/queries.ts`. The page (`SmartCollectionView`) autosaves the query (`createAutosaver`), shows `QueryBuilder` (a "match all/any of these rules" list; **Advanced** adds groups inside groups, turning a group around and several sorts, and stays on for a query that needs it) and `QueryResults`. **A card pool can hold a smart collection**: `collections::may_hold(pool, smart_collection)`; `resolve_cards` runs its query with `only_type = card` right then, so the pool follows the data (a card reached by hand and by a query counts once; an unreadable query makes the draw fail with its message instead of silently drawing less); the Add picker offers smart collections from any library. **Packs** carry `data/smart_collections.json` (optional; still format v1): import drops records for non-collections or unreadable queries with a warning, and rewrites every tag, folder, field and item id inside the query (`remapped_json` with all four maps; a dropdown's choice ids aren't item ids and are untouched). **Search now looks inside field values** (migration 0022 rebuilt `search_index` with a fifth column `fields`, kept current by triggers on `field_values` and `field_definitions`; weighted like tags, so a name match still ranks first; all words may come from the name and the fields together). Not built yet: field views (step 7), a query as a table slot or timeline lane or GM-screen widget source (those tools plug in the same `run_query`), natural number order when sorting text fields in SQL, secret field values are searched and queried like any other (queries only run on the GM's device; filter them when sharing arrives in Phase 9).

- **Content packs** (`src-tauri/src/pack/`, migration 0008): a `.ttrpgpack` file is a zip with `manifest.json` (`format: "ttrpg-toolkit-pack"`, `formatVersion`, `packId`, app/schema versions, project name, counts) plus `data/{folders,items,tags,item_tags,links,documents}.json` (and a reserved `assets/`). The JSON records in `pack/format.rs` are deliberately separate from the DB structs, so DB changes never silently change the file format. **Export** (`export.rs`) writes one whole project including trashed rows. **Import** (`import.rs`) *always creates a new project* "<name> (imported)" with fresh ids (never overwrites), in one transaction (all-or-nothing); items keep `origin_pack_id`/`origin_item_id` for a future "update from original". Reading is separate from writing: `read_pack` enforces size limits (zip-bomb guard), refuses non-packs and packs from a newer `formatVersion`, and *repairs and reports* inconsistent data as warnings (dangling references dropped, parent loops broken, clashing tag names renamed, parents ordered before children). Unknown files/fields are ignored; missing data files count as empty. **Evolving the format:** optional new fields are not breaking (use `#[serde(default)]`); a breaking change bumps `FORMAT_VERSION`, adds an upgrade step in `parse_manifest`, and adds a NEW golden file (`src-tauri/tests/fixtures/pack_v2...`). **Never edit or regenerate `pack_v1.ttrpgpack`**: the `the_committed_version_1_pack_still_imports` test is the promise that old packs keep importing. To add a new kind of data to packs: add its record type and file to `format.rs`, export it, sanitize + import it, extend `populate`/`snapshot` in `pack/tests.rs`. **Ids inside opaque JSON are remapped on import:** saved draws (`result_json`) and decks in play (`state_json`, `source_id`) remember cards by item id, and import gives every item a new id, so `import.rs` rewrites every string that equals an old item id (`remapped_json`; text with nothing to replace is stored byte-for-byte as it was; ids not in the pack, e.g. deleted cards, are left alone and a game's `source_id` becomes null if its source wasn't in the pack). Anything new that stores item ids inside JSON must go through the same rewrite. Files travel to/from Rust as **base64 text** (`src/lib/base64.ts` in JS, `pack::encode_for_transport`/`decode_from_transport` in Rust), never raw bytes. **Android gotcha:** Tauri never delivers a raw request body to commands on Android (`InvokeBody::Raw` is unsupported there; it always sends JSON), so a command taking raw bytes works on Windows and fails on the phone. Any command that moves a file or other binary data must use the text transport; there is one code path for all platforms so tests on Windows cover what the phone runs. JS saves/opens files with the Tauri dialog + fs plugins (verified on Android: content URIs work, `.ttrpgpack` names are kept). The pack commands are `async` so big packs don't freeze the window.
